## Overview

TOM YUM BANG C Restaurant Stock Management System is an internal inventory and purchasing platform designed for day-to-day restaurant operations on a Windows notebook.

The Offline Edition is built around three rules:

1. **The database is the source of truth.**
2. **Confirmed stock movements are immutable.**
3. **AI may analyze and explain data, but AI does not directly modify stock.**

After Docker, the local runtime, and the Ollama model are installed, the restaurant can continue normal stock operations without an Internet connection.

The application is intentionally designed for local use and does not depend on a public server for core inventory operations.

## Core Inventory Principle

Current stock is not stored as an editable number.

It is calculated from the stock movement ledger:

```text
Current Stock = SUM(stock_movements.base_quantity)
```

Example:

```text
Stock In       +10
Stock Out       -2
Waste           -1
Count Variance  -1
-------------------
Current Stock    6
```

Confirmed ledger rows are treated as immutable operational facts.

If a correction is required, the system creates a new movement instead of rewriting historical stock records.

This preserves traceability and makes inventory history auditable.

```text
              |
```

### Network Boundary

The validated offline runtime follows these boundaries:

- The application is published only on `127.0.0.1:3100`.
- Ollama runs as a Docker Compose service and is reached by the application at `http://ollama:11434`.
- Ollama port `11434` is not published to the Windows host or restaurant LAN.
- PostgreSQL is not exposed directly to the LAN.
- Authentication, REST, database, internal gateway, and Ollama services communicate through Docker networks.
- The Ollama model store is persisted in the external Docker volume `tybc_ollama_data`.
- No public Ollama endpoint is required.
- Core restaurant operations and Local AI inference do not require Internet access after installation and model provisioning.

## Local AI

The Offline Edition uses:

```text
Runtime: Docker Compose / Ollama
Model:    qwen3.5:4b
Endpoint: http://ollama:11434 (Docker-internal only)
Volume:   tybc_ollama_data
```

Local AI receives a controlled business-data digest generated by the application.

Its role is to help the OWNER understand information such as:

- low-stock risk
- unusual inventory movement
- waste patterns
- count variance
- operational observations
- purchasing context
- inventory summaries

### AI Safety Boundary

Local AI is intentionally read-only.

AI does not receive unrestricted database write access and must not directly:

- create stock movements
- alter historical ledger rows
- approve purchase orders
- change stock counts
- delete business records
- bypass application validation

Any future AI write capability should pass through validated server-side commands and explicit owner approval.

> The system records facts. The AI explains them.

### Stop the Local Stack

```powershell
cd "D:\TYBC-Dev\tybc-restaurant-stock-offline"

$env:TYBC_DB_VOLUME = "tybc_phase3_rehearsal_db_data"

docker compose `
  -p tybc-phase3-rehearsal `
  --env-file "D:\TomYumBangC\config\phase3-rehearsal.env" `
```

For deployment on another notebook, keep secrets outside the repository and adjust the external environment-file path, Compose project name, database-volume name, and Ollama-volume name for that machine.

## Database and Migration Model

The local PostgreSQL database is rebuilt from repository migrations.

The supported restore strategy is:

```text
Schema = migrations
Data   = data-only backup
```

A schema dump is not used as the primary restore source because it can conflict with migration-managed database objects.

This keeps the database structure reproducible from version-controlled migrations.

## Backup and Restore

Offline backup tooling is stored under:

```text
deploy/offline/production/backup/
```

The package includes:

```text
Backup-Tybc.ps1
Restore-Tybc.ps1
Verify-TybcBackup.ps1
Invoke-TybcRetention.ps1
Invoke-TybcBackup.ps1
```

### Backup Principles

- PostgreSQL backup is data-only.
- Backup archives are stored outside the Git repository.
- Backup integrity is verified.
- SHA-256 is recorded for backup validation.
- Restore is performed into a fresh volume first.
- Restore tooling protects active database volumes from accidental overwrite.
- Database migrations rebuild the schema before data restore.
- Authentication user and identity data required by the offline OWNER workflow are included in the validated backup scope.

Automatic Windows Scheduled Task installation is intentionally not part of the final Offline Edition workflow.

## Security Principles

The Offline Edition follows these operational security rules:

- Keep runtime secrets outside Git.
- Never commit `.env.local`, runtime environment files, database dumps, backup archives, passwords, or access tokens.
- Bind the web application to localhost unless a future security review explicitly approves wider access.
- Keep Ollama on localhost.
- Do not expose PostgreSQL publicly.
- Use RLS and server-side validation for business data.
- Treat stock history as immutable after confirmation.
- AI remains read-only.
- Use a fresh database volume for restore verification.
- Keep backup archives outside the source repository.

The repository is private and intended for authorized TOM YUM BANG C personnel and approved maintainers only.

## Operational Rules

For day-to-day restaurant use:

1. Start Docker Desktop.
2. Confirm Ollama is available.
3. Start the local Compose stack.
4. Open `http://127.0.0.1:3100`.
5. Sign in with the authorized OWNER account.
6. Record real stock operations through the application.
7. Use Local AI for analysis, not for direct stock modification.
8. Create and verify backups according to the restaurant backup routine.
9. Stop the local stack with Compose when required, without deleting the persistent volume.
